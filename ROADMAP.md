## Independent product & engineering review — 2026-09-13
Two independent, deliberately adversarial review agents (no shared context with each other or with the agents that built the features above) were dispatched against the live codebase: one a product/pedagogy critique (is this actually good ed-tech, competitively and ethically), one an engineering/security/architecture critique (is this actually production-ready). Full findings are in the session transcript; the critical issues below were reviewed and, where marked, turned into concrete Phase 7 work. Two decisions came out of this that are worth recording explicitly so they don't get silently "fixed" by a future pass over the critique:

- **Decision — no AI-disclosure watermarking on generated research papers.** The product critique's top finding was that `write_research_paper` produces a submission-ready PDF with no disclosure/watermark/honor-code language, and recommended adding one. Deliberately rejected: every frontier AI provider can already produce a comparable LaTeX paper quickly on request, so singling this one feature out with a disclosure stamp doesn't change the competitive reality or meaningfully deter misuse — it just adds friction to legitimate use (outlining, drafting help, citation-backed synthesis of a student's own research). Policy instead: monitor for real abuse and remove or restrict the feature if it actually becomes a problem, rather than pre-emptively degrading it on a hypothetical.
- **Decision — no flat spend cap on `write_research_paper`; a prepaid-credit top-up system instead.** The engineering critique flagged that the tool has no cost ceiling of its own (unlike `research_fetch`'s explicit 15-calls-per-session limit). ## Phase 13 — Most tools loaded on-demand instead of on every turn (`use_capability`), MAX_TOOL_ROUNDS raised for the extra round it costs

## Phase 15 — Message editing: edit a previous message, permanently discard its reply and everything after

Product-owner decision, matching Claude/ChatGPT/Gemini's actual behavior, simpler of two possible designs deliberately chosen: a student can edit a PREVIOUS message they sent. Editing it **permanently discards** that message's original reply and everything after it in the session (no branch history, no undo, no left/right version arrows — that needs a real tree schema, deliberately out of scope) — the edited text is then resent exactly like a brand new message.

- ! **Backend — a real message id, and a clean, minimal delete-and-truncate addition.** `ChatMessage` already had a real UUID primary key; `GET /chat/sessions/{id}/messages` (`list_messages`) now exposes it as `id` in each returned object — the truncation-point identity this feature needs, since `created_at` string-matching across client/server round-trips is not guaranteed unique/orderable. New `DELETE /chat/sessions/{session_id}/messages/{message_id}` (`delete_message_and_after`) deletes the target message and every later message (by `created_at`, with the target's own id as an equality tiebreaker for the practically-impossible duplicate-timestamp case) in one `DELETE ... WHERE` statement — not a loop of individual deletes, so there's no window where a concurrent read could observe a partially-truncated history — then invalidates the session's Tier-1 Redis working-memory bundle (`app/memory/working.py`'s `invalidate`, the same cleanup `delete_session` already does) so the next turn rebuilds fresh from Postgres instead of resending now-discarded turns as context. Same ownership-check pattern (`require_user` + `session.user_id == user.id`, 404 otherwise) every other per-session endpoint already uses. Read every migration before writing this: confirmed nothing else in this schema references a `chat_messages` row by id (`profile_facts.source_session_id`/`session_summaries.session_id` both reference a *session*, migration `0004`) — no cascade concerns beyond the `chat_messages` table itself, no new migration needed.
- ! **The WS handler now echoes a just-persisted user message's real id immediately** (`chat_ws` sends a new `{"type": "user_message_saved", "id": ...}` frame right after the user turn commits, before the crisis check or `run_tutor` even starts) — without this, a student couldn't edit the message they *just* sent without first switching sessions and back to force a history refetch. ## Phase 17 — Two more live-tested product-owner bugs: the chat socket never recovers from backgrounding, and the Notepad's sign-in race

Two concrete, verbatim reports: "If you tab out and go to another tab, the connected goes to offline/disconnected, even though im connected to the internet etc" and "can't use the notepad, because it says Waiting for the main Newton window to sign in... - even tho im signed in. There should be a sign-in button there as well." Both root causes were confirmed by direct code reading before touching anything, and both turned out to be real logic bugs, not display bugs:

- ! **Root cause 1 — no keepalive, no reconnect, anywhere.** `App.tsx`'s WS effect set `ws.onclose = () => setWsStatus("closed")` and nothing else. Once *anything* closed the socket (background-tab power throttling is the likely real cause given the report, but an SSH tunnel's own idle timeout or a proxy could equally do it — the exact layer doesn't matter, since **nothing was generating any traffic to prevent an idle-timeout closure from any of them in the first place**), the app sat in `"closed"` forever until something incidental (switching chats) re-ran the effect. Fixed both halves:
  - **Keepalive**: the client now sends `{"type": "ping"}` every 25s while connected; `services/api/app/routers/chat.py`'s `chat_ws` acks it with `{"type": "pong"}` in the idle-loop branch. A ping landing **mid-generation** (the recv/gen race loop) deliberately gets **no** explicit pong — `_drain_generation` is already streaming real `chunk` frames concurrently on the same socket at that point, which already satisfies the keepalive's purpose, and replying from the recv-loop side too would race `_drain_generation`'s own concurrent `websocket.send_json` calls (an existing, documented invariant in that code — "no safe way to interleave a second send on this socket while `_drain_generation` may itself be mid-send").
  - **Reconnect**: a `torndown` flag (not the previous `cancelled` naming) now distinguishes a deliberate teardown (unmount, or `activeSessionId` changing) from a real unexpected close. Only the latter schedules a reconnect, with a capped exponential backoff (1s → 2s → 4s → ... → 30s cap), always via `tokenManager.getValidAccessToken()` for a guaranteed-fresh token rather than a closed-over one. A `document.visibilitychange`/`focus` listener additionally triggers an **immediate** reconnect attempt (bypassing whatever's left of the backoff delay) the moment the app regains focus — the exact "tab back in" scenario reported. A new `"reconnecting"` `ConnectionStatus` (distinct from the initial `"connecting"`) is now shown in the existing header dot/label while a reconnect attempt is in flight, instead of just sitting on `"offline"` the whole time.
- ! **Root cause 2 — a real race, not a display bug.** `App.tsx`'s `useEffect(() => {...emit("notepad-auth", {token})}, [token])` fires **only** when `token` itself changes (sign-in, or roughly hourly on background refresh). `NotepadWindow.tsx` only starts listening for that event once it mounts. Tauri events are **not queued for late listeners** — a Notepad opened well after sign-in (the normal case: sign in, work in the main window a while, *then* open the Notepad) had already missed the one broadcast that mattered and would sit on "waiting" for up to an hour, even though the main window was genuinely signed in the entire time. ## Phase 18 — Cost investigation: waking up the dead Tier-2 consolidation trigger, and empirically checking whether OpenRouter's DeepSeek route actually caches the repeated system-prompt prefix

A PM-level investigation found a real, measured cost problem: `app/memory/working.py`'s Tier-1 bundle is a plain `MAX_TURNS = 20`-capped sliding window (no summarization), and `app/jobs/consolidate.py`'s `consolidate_session` — a real, well-tested job that re-summarizes a session's full transcript and upserts durable facts into Tier 3 — only ever fired from `POST /chat/sessions/{id}/end`, which nothing in the real desktop app calls (`endSession()` exists in `apps/desktop/src/api.ts`, has a test mock, and is invoked from no real UI action). So the one safety net against turns silently aging out of the window with zero record had essentially never run in production.

**Task 1 — wire the real trigger.** `app/routers/chat.py`'s WS handler now enqueues the exact same `consolidate_session` job (same `pool.enqueue_job("consolidate_session", str(session_id))` call the dead end-of-session path already used) periodically instead, driven by a new `turns_since_consolidation` counter `app/memory/working.py`'s `append_turn` maintains on the Redis bundle — incremented on every appended turn (unlike the capped `turns` list itself, so it keeps counting past MAX_TURNS instead of latching). `should_consolidate()`/`mark_consolidated()` (also in `working.py`) check/reset it; `mark_consolidated` resets synchronously at enqueue time in the WS handler, not inside the job, so "don't fire again too soon" never depends on the job's own unrelated completion timing — genuinely fire-and-forget (`pool.enqueue_job` is one fast Redis write, never awaited to completion).

- **Chosen interval: `CONSOLIDATION_INTERVAL_TURNS = MAX_TURNS` (20 turns / ~10 exchanges)**, i.e. first fire the moment the window first fills, then again every 20 turns after (40, 60, 80, ...). Reasoning (documented in `working.py`): `consolidate_session` is one real model call over the whole transcript so far — real cost, but a single call — so firing it this rarely means it amortizes over at least ~10 of the window-full turns it exists to eventually let shrink (lowering `MAX_TURNS` itself is a deliberate, separate follow-up once this is proven live, not bundled in here).
- **Two latent bugs this surfaced and fixed**, both required for "call it repeatedly over a growing session" to actually be safe (not just the fact-dedup path the investigation already flagged):
  - `consolidate_session` used to call `working.invalidate()` at the end, deleting the **entire** Tier-1 bundle. Harmless at a real session's end; actively harmful mid-session, since `app.agents.tutor.run_tutor`'s only source of recent-conversation context is that bundle's `turns` list, with no Postgres fallback — it would have silently erased the model's memory of the conversation so far every time consolidation ran. Removed; the other half of what it was for (fresh profile facts, not stale ones) is already handled unconditionally every turn regardless (`_gather_memory_context` + `set_profile_facts`/`set_retrieved_chunks`).

Now reads the existing row first and updates it in place if present.

## Phase 19 — Fixing a real, confirmed bug: returning to a chat after a few hours wiped the Tutor's memory of it

A PM-level investigation found: `app/memory/working.py`'s `get_bundle(session_id)` reads a Redis-cached Tier-1 bundle (`BUNDLE_TTL_SECONDS`, 2 hours) holding the session's recent raw turns. If that Redis key was missing or expired, `get_bundle` silently returned a plain empty default — **no fallback to Postgres at all** — and `app.agents.tutor.run_tutor` only ever reads `bundle["turns"]`, never `ChatMessage` directly. Net effect: any student who closed the app and came back after more than 2 hours idle (ordinary usage) to keep chatting in the same existing thread got a Tutor with genuinely zero memory of that conversation on the very next turn, even though the full transcript was sitting right there in Postgres and visibly rendered in their own sidebar.

**The fix.** `get_bundle` now rehydrates from Postgres on a cold cache: pulls back the most recent `MAX_TURNS` messages (the same window size the live sliding-window mechanism already caps `turns` at) for a session that actually has history, rebuilds `bundle["turns"]` in correct chronological order, resets `turns_since_consolidation` to 0 (the durable Tier-3 facts layer, not this counter, is what's supposed to carry "what we covered before this gap" across a cold start), and caches the rebuilt bundle straight back into Redis so the Postgres round trip is paid once per cold start, not every turn. A genuinely new/empty session still costs exactly one cheap existence-confirming query and gets no Redis write, unchanged from before.

Rehydration lives in exactly one place — `app/memory/working.py`'s private `_get_bundle`/`_rehydrate_from_postgres` — rather than threading a DB session through `get_bundle`'s signature or special-casing `run_tutor`'s own call site. That mattered concretely: `app/routers/chat.py`'s WS handler calls `append_turn` with the student's new message *before* it calls `run_tutor`, and `append_turn` itself calls `get_bundle` internally — so a rehydration fix scoped only to `run_tutor`'s call would already be looking at a cache `append_turn` had just warmed (with a single-turn bundle) moments earlier, never actually triggering.

**A real bug this surfaced during the fix, caught by CI, not shipped:** every real call site (`chat.py`'s WS handler, in all three places it calls `append_turn`) always persists a `ChatMessage` row to Postgres and commits it *before* calling `append_turn` for that same turn. On a cold cache, that meant `_rehydrate_from_postgres`'s query already picked up the just-committed row as Postgres's newest message, and `append_turn` appending it again on top duplicated the tail of `turns`. Fixed with a narrow dedup guard: `_get_bundle` (private) reports whether it just rehydrated from a cold cache; `append_turn` uses that flag — never applied on the normal warm-cache path — to drop an exact tail duplicate before appending its own turn. First CI push caught this via the pre-existing `test_jobs_consolidate.py` regression test; a second push fixed a related test-only issue (`_add_messages` batching multiple rows into one Postgres transaction, all landing on the same `now()` timestamp — real production traffic never ties like this, since `chat.py` commits each turn separately).

## Independent product & engineering review — 2026-09-17
Two independent, deliberately adversarial review agents (no shared context with each other), dispatched against the current live codebase — one a product/pedagogy/competitive critique (is Newton actually winning against the "just use a chatbot" alternative, per the explicit product direction to be "what Cursor is for coding, but for learning"), one an engineering/security/architecture critique, mirroring the Phase 6.5 review's format exactly. **Product/pedagogy findings** (most important first):
1. **The core "verified, not vibes" claim is invisible to the student.** `tutor.py`'s system prompt never instructs the model to *tell* a student a math answer was SymPy-verified — `check_student_work`'s tool result literally contains `"CORRECT. Verified via symbolic math..."`, but the model is told to "give brief, encouraging confirmation," and paraphrases the fact away. Every tool call renders through the identical generic `tool-activity-chip` styling regardless of whether the underlying result was computationally guaranteed or an LLM judgment call. A skeptical parent or teacher cannot currently tell, from the product itself, when an answer is mathematically certain versus merely plausible-sounding. Not yet fixed — tracked as the top candidate for Phase 26.
2. **Focus Mode and Learn Mode are opt-in, off by default, and self-reported.** `FOCUS_MODE_SYSTEM_ADDENDUM` explicitly tells the model to hand over the direct answer once a student says they want their attempt checked or just want the answer — a determination the model itself makes with no server-side enforcement. The median homework-help session (both modes off, which is the default) is functionally identical to pasting into a generic chatbot.
3. **Onboarding cannot demonstrate the actual competitive moat.** The four example prompts deliberately avoid flashcards/study-plans/exams (Phase 7's own note: they need an uploaded document a first-run account doesn't have). A brand-new student's first five minutes show tool-calling parity with a generic chatbot, never the syllabus→plan→spaced-repetition→adaptive-difficulty loop that's the actual differentiator.
4. **`write_research_paper` has zero computational grounding** — the tool a skeptical parent/teacher would scrutinize hardest is pure "trust the model," same architecture as a bare chatbot with better bibliography formatting.
5. **The new quiz artifact kind risks converging toward generic AI capability** rather than away from it — partially mitigated already, see Phase 23's quiz-grounding entry above and the prompt steering that favors FSRS-backed tools first.
6. **The Home dashboard's weak-areas widget doesn't close its own loop** — its buttons open generic panels instead of a session pre-filtered to the specific weak topic surfaced. See Phase 21.
7. **ROADMAP.md's own evidentiary discipline had lapsed** for the newest, highest-risk work — the finding this entire retroactive-documentation pass (Phases 21-24 above) exists to address.

**Engineering/security findings** (most severe first):
1. **Chat WebSocket auth token leaks into logs via URL query string.** `apps/desktop/src/api.ts`'s `wss://…/chat/ws/{sessionId}?token=<JWT>` plus uvicorn's default access logger writing the full request line to stdout on every handshake — and Phase 17's reconnect/keepalive work made these sockets reconnect far more often, multiplying exposure. **Fixed in a later session** (2026-09-18): `--no-access-log` added immediately as the safe stopgap, then the full fix — `chat_ws` now accepts unconditionally and expects `{"type": "auth", "token": "..."}` as the first frame over the connection instead of a query parameter (`apps/desktop/src/api.ts`'s `openChatSocket` no longer takes a token at all; `App.tsx` sends it from `onopen` and gates real "connected" status — and `handleSend`/`handleStop` — on a new `auth_ok` frame via `wsAuthedRef`, not on the raw WebSocket `readyState` alone, since that goes `OPEN` before the application-level handshake completes). All ~9 backend WS test call sites and the frontend's WS mock/reconnect tests updated to the new protocol; verified against the real deployed dev box (`tsc` clean, 662/662 frontend, 862+/864 backend passing — same pre-existing/flaky exceptions as every other recent phase), CI green.
2. **No concurrency guard on frontier-model billing — a real TOCTOU gap.** `frontier_access_available` checks the balance fresh per turn, but `record_frontier_usage` only debits after the whole turn finishes (25-110s later for a multi-tool-call turn); concurrent sessions all read the same pre-spend balance and can all pass the check before any of them writes back. This undermines the Phase 6.5 review's own stated reason for choosing prepaid top-ups over a hard cap — the balance isn't actually enforced under concurrency. Not yet fixed.
3. **Tauri's fs-write permission has no scope, and CSP is `null`.** `capabilities/default.json` grants `fs:allow-write-file` with no `fs:scope` at all, confirmed against the plugin's own permission doc ("without any pre-configured scope"); `tauri.conf.json` sets `"security": {"csp": null}`. Not exploitable today (the markdown pipeline renders no raw HTML, KaTeX `trust` is off) but there is currently nothing standing between a future XSS and unrestricted file writes on a student's disk.
