- # LaTeX compile sandbox + secure research-fetch tool — `sandbox-runner` gains `POST /compile-latex`, extending its existing isolation pattern (non-root, dropped capabilities, read-only fs, `preexec_fn` rlimits, a process-group wall-clock watchdog) rather than a second sandboxing mechanism; TeX Live installed via apt with a hand-picked package set (`texlive-latex-base/-recommended/-extra`, `texlive-publishers` for IEEEtran/acmart, `texlive-humanities` for apa7, `texlive-bibtex-extra` + `biber`), independent `LATEX_*` rlimit/timeout tunables (a real multi-pass compile needs far more time/files/memory than a short Python script), `-no-shell-escape` stated explicitly on every `pdflatex` invocation regardless of the distro default, an in-code engine allowlist so the caller-supplied `engine` field is never interpolated into a subprocess command line, and the standard `pdflatex → biber → pdflatex → pdflatex` pass sequence for citations/cross-references. ## Independent product & engineering review — 2026-09-13
Two independent, deliberately adversarial review agents (no shared context with each other or with the agents that built the features above) were dispatched against the live codebase: one a product/pedagogy critique (is this actually good ed-tech, competitively and ethically), one an engineering/security/architecture critique (is this actually production-ready). Full findings are in the session transcript; the critical issues below were reviewed and, where marked, turned into concrete Phase 7 work. Two decisions came out of this that are worth recording explicitly so they don't get silently "fixed" by a future pass over the critique:

- **Decision — no AI-disclosure watermarking on generated research papers.** The product critique's top finding was that `write_research_paper` produces a submission-ready PDF with no disclosure/watermark/honor-code language, and recommended adding one. Deliberately rejected: every frontier AI provider can already produce a comparable LaTeX paper quickly on request, so singling this one feature out with a disclosure stamp doesn't change the competitive reality or meaningfully deter misuse — it just adds friction to legitimate use (outlining, drafting help, citation-backed synthesis of a student's own research). Policy instead: monitor for real abuse and remove or restrict the feature if it actually becomes a problem, rather than pre-emptively degrading it on a hypothetical.
- **Decision — no flat spend cap on `write_research_paper`; a prepaid-credit top-up system instead.** The engineering critique flagged that the tool has no cost ceiling of its own (unlike `research_fetch`'s explicit 15-calls-per-session limit). A hard per-call/per-day cap was considered and rejected — legitimate deep-research use can genuinely need more tokens than an arbitrary number would allow, and an arbitrary cap punishes exactly the use case this tool exists for. See Phase 7's credit top-up item for the chosen alternative.

## Phase 9 — Chat UX: real perf fix + the "streaming feels fake" root causes

Commissioned by a product-owner adversarial UX critique (a demanding-power-user role-play, grounded in real code reads) that traced "streaming feels fake" to three distinct, real root causes, plus confirmed two missing features (a visible "thought process," smart conversation titles). - # **Killed a real perf bug, not just UX polish: blocking embedding calls on every chat turn.** `app/memory/embeddings.py`'s `embed_text` ran fastembed's ONNX inference synchronously inline inside the async request coroutine — no `asyncio.to_thread` anywhere — blocking the ENTIRE event loop (every other connected student's WebSocket too) on CPU-bound inference, twice, sequentially, before the tutor's own model call even started. Fixed in two parts: `embed_text` now offloads the real inference via `asyncio.to_thread`; `app/routers/chat.py`'s new `_gather_memory_context` fires the profile-facts and RAG-chunks retrievals concurrently via `asyncio.gather` (each on its own short-lived `AsyncSession`, since a single `AsyncSession` forbids concurrent use — reusing the WS handler's own session across a `gather()` would have been a second, subtler bug). **CI caught a real concurrency bug this introduced before it reached anyone**: the very first embed of a process could have two `asyncio.to_thread` worker threads both see the shared embedder as uninitialized and race to construct it at once, which crashed with `AttributeError: type object 'tqdm' has no attribute '_lock'` (a real bug in tqdm's own locking under exactly this kind of concurrent first-use during fastembed's model-download path) — fixed with a proper double-checked lock in `_get_embedder` (a plain `functools.lru_cache` does not prevent concurrent calls to the wrapped function on a cache miss), with a regression test hammering it from 8 threads at once. ## Phase 13 — Most tools loaded on-demand instead of on every turn (`use_capability`), MAX_TOOL_ROUNDS raised for the extra round it costs

Built Newton's own version: `CORE_TOOL_NAMES` (`calculator`/`unit_converter`/`symbolic_math`/`web_search`) plus a new `use_capability` meta-tool are the only things sent by default; every other registered tool (`plot_function`, `code_interpreter`, `research_fetch`, `textbook_lookup`, `start_study_session`, `grammar_check`, `format_citation`, `generate_flashcards`, `generate_practice_exam`, `generate_study_plan`, `sync_google_classroom`, `check_student_work`, `get_weak_areas`, `get_math_hint`, `write_research_paper`) is withheld until the model calls `use_capability` naming what it needs (one call can name several at once — its own description explicitly says so, to avoid burning a round per tool). `read_image` is the one deliberate exception: included directly whenever `app/agents/tutor.py`'s new `_IMAGE_ATTACHMENT_RE` finds a real `"[Attached image: <id>]"` marker in the message (the same marker `app/routers/chat.py`'s upload endpoint already puts there) — a deterministic, cheap, application-level fact, never worth a model round-trip to discover.

## Phase 15 — Message editing: edit a previous message, permanently discard its reply and everything after

Product-owner decision, matching Claude/ChatGPT/Gemini's actual behavior, simpler of two possible designs deliberately chosen: a student can edit a PREVIOUS message they sent. Editing it **permanently discards** that message's original reply and everything after it in the session (no branch history, no undo, no left/right version arrows — that needs a real tree schema, deliberately out of scope) — the edited text is then resent exactly like a brand new message.

- # **Backend — a real message id, and a clean, minimal delete-and-truncate addition.** `ChatMessage` already had a real UUID primary key; `GET /chat/sessions/{id}/messages` (`list_messages`) now exposes it as `id` in each returned object — the truncation-point identity this feature needs, since `created_at` string-matching across client/server round-trips is not guaranteed unique/orderable. New `DELETE /chat/sessions/{session_id}/messages/{message_id}` (`delete_message_and_after`) deletes the target message and every later message (by `created_at`, with the target's own id as an equality tiebreaker for the practically-impossible duplicate-timestamp case) in one `DELETE ... WHERE` statement — not a loop of individual deletes, so there's no window where a concurrent read could observe a partially-truncated history — then invalidates the session's Tier-1 Redis working-memory bundle (`app/memory/working.py`'s `invalidate`, the same cleanup `delete_session` already does) so the next turn rebuilds fresh from Postgres instead of resending now-discarded turns as context. Same ownership-check pattern (`require_user` + `session.user_id == user.id`, 404 otherwise) every other per-session endpoint already uses. Read every migration before writing this: confirmed nothing else in this schema references a `chat_messages` row by id (`profile_facts.source_session_id`/`session_summaries.session_id` both reference a *session*, migration `0004`) — no cascade concerns beyond the `chat_messages` table itself, no new migration needed.
- # **The WS handler now echoes a just-persisted user message's real id immediately** (`chat_ws` sends a new `{"type": "user_message_saved", "id": ...}` frame right after the user turn commits, before the crisis check or `run_tutor` even starts) — without this, a student couldn't edit the message they *just* sent without first switching sessions and back to force a history refetch. Fires on every user turn including a crisis-response one; existing WS tests' strict frame-type-set assertions were updated for the new frame type, not weakened.
- # **Frontend — `ContextMenu.tsx` gains "Edit message"**, gated to `role === "user"` messages that already carry a real, persisted id (`MessageBubble.tsx` now sets `data-message-role`/`data-message-id`), and disabled (not hidden) while `isStreaming` — same gate Composer already applies to sending a new message. Clicking it (`App.tsx`'s `handleEditMessage`) sets `editingMessage` state and focuses the composer; `Composer.tsx`'s new `editing` prop repopulates the draft with that message's *exact* original text (a `useEffect` keyed on `editing.id` alone, so further student tweaks mid-edit are never stomped by an unrelated re-render) and renders an "Editing message" banner with a Cancel button that clears the draft and backs out without sending anything. `App.tsx`'s `handleSend` is the single send path for both a normal message and an edit — Composer never calls a separate function: when `editingMessage` is set, it `await`s `deleteMessageAndAfter` FIRST; only on success does it truncate the local `messages` array (`slice(0, idx)`) and fall through to the exact same optimistic-append-then-`socket.send` code every other message already uses. A failed delete sets an inline `editError` (shown in the same banner) and returns immediately — no truncation, no send, original conversation completely untouched.
- # **Incidental bug fix surfaced by writing the resend test**: `MessageContent.tsx`'s streaming-debounce (`STREAMING_DEBOUNCE_MS`) assumed a component instance always belongs to the same logical message across its lifetime — true for every prior feature (messages are only ever appended, never removed-then-replaced at the same array index) but false the instant an edit truncates and immediately re-appends at the same index: React (matched by `ChatPane`'s `key={index}`) reuses the old `MessageContent` instance, and the debounce would leave the *previous, unrelated* message's rendered text on screen for up to 50ms after the new streaming placeholder had already started. Fixed by bypassing the debounce whenever content is blank (a real stream's content only ever grows, so blank-while-streaming can only mean a fresh start, never a mid-stream event worth coalescing) — caught by a real assertion in the automated edit-and-resend test, not observed by hand.
