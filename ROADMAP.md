## Phase 6 — Research Paper Writer
- # LaTeX compile sandbox + secure research-fetch tool — `sandbox-runner` gains `POST /compile-latex`, extending its existing isolation pattern (non-root, dropped capabilities, read-only fs, `preexec_fn` rlimits, a process-group wall-clock watchdog) rather than a second sandboxing mechanism; TeX Live installed via apt with a hand-picked package set (`texlive-latex-base/-recommended/-extra`, `texlive-publishers` for IEEEtran/acmart, `texlive-humanities` for apa7, `texlive-bibtex-extra` + `biber`), independent `LATEX_*` rlimit/timeout tunables (a real multi-pass compile needs far more time/files/memory than a short Python script), `-no-shell-escape` stated explicitly on every `pdflatex` invocation regardless of the distro default, an in-code engine allowlist so the caller-supplied `engine` field is never interpolated into a subprocess command line, and the standard `pdflatex → biber → pdflatex → pdflatex` pass sequence for citations/cross-references. Paired with `research_fetch` (`app/tools/research_fetch.py`): fetches full source text (not just SearXNG snippets) from a curated, hand-edited domain allowlist (arxiv.org, PubMed/PMC, doi.org, Wikipedia, Semantic Scholar, PLOS, `*.edu`), with real SSRF/DNS-rebinding defense (resolve once via `socket.getaddrinfo`, reject any private/loopback/link-local/multicast/reserved address, then connect directly to the validated IP so there's no re-resolution window for a rebinding attacker to exploit), redirects re-validated through the same pipeline before being followed (capped at 3 hops), https-only, a streamed hard size cap, a content-type allowlist, returned content wrapped as explicitly untrusted external material, and a Redis-backed per-session rate limit. ## Independent product & engineering review — 2026-09-13
Two independent, deliberately adversarial review agents (no shared context with each other or with the agents that built the features above) were dispatched against the live codebase: one a product/pedagogy critique (is this actually good ed-tech, competitively and ethically), one an engineering/security/architecture critique (is this actually production-ready). Full findings are in the session transcript; the critical issues below were reviewed and, where marked, turned into concrete Phase 7 work. Two decisions came out of this that are worth recording explicitly so they don't get silently "fixed" by a future pass over the critique:

- **Decision — no AI-disclosure watermarking on generated research papers.** The product critique's top finding was that `write_research_paper` produces a submission-ready PDF with no disclosure/watermark/honor-code language, and recommended adding one. Deliberately rejected: every frontier AI provider can already produce a comparable LaTeX paper quickly on request, so singling this one feature out with a disclosure stamp doesn't change the competitive reality or meaningfully deter misuse — it just adds friction to legitimate use (outlining, drafting help, citation-backed synthesis of a student's own research). Policy instead: monitor for real abuse and remove or restrict the feature if it actually becomes a problem, rather than pre-emptively degrading it on a hypothetical.
- **Decision — no flat spend cap on `write_research_paper`; a prepaid-credit top-up system instead.** The engineering critique flagged that the tool has no cost ceiling of its own (unlike `research_fetch`'s explicit 15-calls-per-session limit). A hard per-call/per-day cap was considered and rejected — legitimate deep-research use can genuinely need more tokens than an arbitrary number would allow, and an arbitrary cap punishes exactly the use case this tool exists for. See Phase 7's credit top-up item for the chosen alternative.

All other critical issues from both reviews (secrets defaults, JWT algorithm pinning, account deletion, CI/CD's dependence on the shared dev box, backups, monitoring, dependency scanning, onboarding, parent/teacher visibility, moderation/crisis-response) were agreed with as real gaps — tracked below. Audited 2026-09-13 against both full review reports to confirm every critical issue and missing-feature/-infrastructure item from each has a line item here (not just the ones already called out in the first pass) — additions from that audit are marked below.

- **Decision — Meta Muse Spark 1.3 Contributor added to the Pro model roster, no disclosure to students/parents.** Same review conversation surfaced this model as a genuine DeepSeek-tier price/performance competitor ($0.10/$0.20 per million, confirmed the identical weights to the $4.25/M standard tier). Its low price is Meta's compensation for training-data consent — Contributor-tier prompts/completions are usable for training, unlike Standard Services, and Meta's own docs warn against sending sensitive content through it. Flagged explicitly (real student conversations would become Meta training data with no disclosure); the product owner chose to proceed on the price/performance case anyway, without disclosure. - # Account deletion + FK cascade audit — migration 0010 put `ondelete="CASCADE"` on all 8 `user_id` foreign keys that had none (`chat_sessions`, `documents`, `study_plan_items`, `google_classroom_connections`, `flashcards`, `flashcard_review_logs`, `practice_exams`, `profile_facts` — all owned content, so CASCADE is correct for every one, unlike `study_plan_items`/`chat_sessions`' existing `document_id`/child-table patches, which are a different column and stay as they were). Live verification surfaced one more real gap the audit missed: `document_chunks.document_id` (not a `user_id` FK, but a transitive dependency of `documents`) also had no `ondelete`, so cascading a user's documents away still hit an `IntegrityError` on their chunks — fixed in a follow-up migration 0011, same CASCADE reasoning. `DELETE /account` (`app/routers/account.py` + `app/services/account.py`) requires auth, takes no target-user parameter (deletes only the caller's own row), reads each Document's `minio_key` before deleting the user so the now-orphaned MinIO objects can be removed after the DB cascade commits (MinIO isn't part of the Postgres transaction), and leaves the Keycloak identity itself untouched — this app has no Keycloak admin-API integration anywhere yet, so that's explicitly scoped out for a later pass rather than silently skipped. Tested at every layer (cascade genuinely empties all 8 tables plus `document_chunks` for a real user with real rows in each, including a self-referential `profile_facts.superseded_by` pair; the empty-user case; auth-required; no other-user-id path exists) and verified live end-to-end against the real deployed stack: a real disposable Keycloak user (never `student1`) with a real uploaded document + MinIO object, chat session, flashcard + review, and practice exam, deleted through the real `DELETE /account` call — confirmed by direct Postgres and MinIO queries afterward that every row and the MinIO object were actually gone, and that the Keycloak identity itself, as documented, was not.
- ! - !
