- # LaTeX compile sandbox + secure research-fetch tool — `sandbox-runner` gains `POST /compile-latex`, extending its existing isolation pattern (non-root, dropped capabilities, read-only fs, `preexec_fn` rlimits, a process-group wall-clock watchdog) rather than a second sandboxing mechanism; TeX Live installed via apt with a hand-picked package set (`texlive-latex-base/-recommended/-extra`, `texlive-publishers` for IEEEtran/acmart, `texlive-humanities` for apa7, `texlive-bibtex-extra` + `biber`), independent `LATEX_*` rlimit/timeout tunables (a real multi-pass compile needs far more time/files/memory than a short Python script), `-no-shell-escape` stated explicitly on every `pdflatex` invocation regardless of the distro default, an in-code engine allowlist so the caller-supplied `engine` field is never interpolated into a subprocess command line, and the standard `pdflatex → biber → pdflatex → pdflatex` pass sequence for citations/cross-references. ## Independent product & engineering review — 2026-09-13
Two independent, deliberately adversarial review agents (no shared context with each other or with the agents that built the features above) were dispatched against the live codebase: one a product/pedagogy critique (is this actually good ed-tech, competitively and ethically), one an engineering/security/architecture critique (is this actually production-ready). Full findings are in the session transcript; the critical issues below were reviewed and, where marked, turned into concrete Phase 7 work. Two decisions came out of this that are worth recording explicitly so they don't get silently "fixed" by a future pass over the critique:

- **Decision — no AI-disclosure watermarking on generated research papers.** The product critique's top finding was that `write_research_paper` produces a submission-ready PDF with no disclosure/watermark/honor-code language, and recommended adding one. Deliberately rejected: every frontier AI provider can already produce a comparable LaTeX paper quickly on request, so singling this one feature out with a disclosure stamp doesn't change the competitive reality or meaningfully deter misuse — it just adds friction to legitimate use (outlining, drafting help, citation-backed synthesis of a student's own research). Policy instead: monitor for real abuse and remove or restrict the feature if it actually becomes a problem, rather than pre-emptively degrading it on a hypothetical.
- **Decision — no flat spend cap on `write_research_paper`; a prepaid-credit top-up system instead.** The engineering critique flagged that the tool has no cost ceiling of its own (unlike `research_fetch`'s explicit 15-calls-per-session limit). A hard per-call/per-day cap was considered and rejected — legitimate deep-research use can genuinely need more tokens than an arbitrary number would allow, and an arbitrary cap punishes exactly the use case this tool exists for. See Phase 7's credit top-up item for the chosen alternative.

## Phase 9 — Chat UX: real perf fix + the "streaming feels fake" root causes

Commissioned by a product-owner adversarial UX critique (a demanding-power-user role-play, grounded in real code reads) that traced "streaming feels fake" to three distinct, real root causes, plus confirmed two missing features (a visible "thought process," smart conversation titles). This phase fixes exactly those four items. Explicitly OUT OF SCOPE for this pass (see the critique's other findings, deliberately deferred to a documented next wave): regenerate/edit-resend a message, chat keyboard shortcuts, a stopped-message ellipsis indicator, and skeleton loading states — one line each below.

- # **Killed a real perf bug, not just UX polish: blocking embedding calls on every chat turn.** `app/memory/embeddings.py`'s `embed_text` ran fastembed's ONNX inference synchronously inline inside the async request coroutine — no `asyncio.to_thread` anywhere — blocking the ENTIRE event loop (every other connected student's WebSocket too) on CPU-bound inference, twice, sequentially, before the tutor's own model call even started. Fixed in two parts: `embed_text` now offloads the real inference via `asyncio.to_thread`; `app/routers/chat.py`'s new `_gather_memory_context` fires the profile-facts and RAG-chunks retrievals concurrently via `asyncio.gather` (each on its own short-lived `AsyncSession`, since a single `AsyncSession` forbids concurrent use — reusing the WS handler's own session across a `gather()` would have been a second, subtler bug). **CI caught a real concurrency bug this introduced before it reached anyone**: the very first embed of a process could have two `asyncio.to_thread` worker threads both see the shared embedder as uninitialized and race to construct it at once, which crashed with `AttributeError: type object 'tqdm' has no attribute '_lock'` (a real bug in tqdm's own locking under exactly this kind of concurrent first-use during fastembed's model-download path) — fixed with a proper double-checked lock in `_get_embedder` (a plain `functools.lru_cache` does not prevent concurrent calls to the wrapped function on a cache miss), with a regression test hammering it from 8 threads at once. Tests: `test_memory_embeddings.py` (non-blocking behavior + the thread-safety regression, DB-independent, run and passing locally) and `test_chat_memory_gather.py` (the concurrent-fetch behavior and its "separate session per retrieval" safety property, also DB-independent and passing locally) — both exercised for real by live traffic against the deployed dev box below, with no further errors.
- # **Honest streaming dots.** `MessageBubble.tsx`'s `.streaming-dots` used to render for the entire duration `message.streaming` was true, contradicting text/tool-activity/plan content that had already visibly landed above it. Now hidden the moment any of text, tool activity, or the new plan-narration chip (below) has arrived — `showStreamingDots = message.streaming && !hasRealContent && !hasActivity && !hasPlanNarration`. Kept the existing `transcript-streaming-pulse` border animation as the sole remaining "still active" signal once the dots are gone, rather than stacking two redundant ones.
- # **Debounced the markdown re-parse during streaming.** `MessageContent.tsx` used to re-run the full `ReactMarkdown` parse (remarkGfm + remarkMath + rehypeKatex + rehypeHighlight — real, repeated CPU work, especially `rehypeHighlight`'s syntax tokenizing) on the entire accumulated string on every single incoming token. Now debounces the re-render on a 50ms trailing edge while a new `streaming` prop is true; the non-streaming render path (history, finished replies) is untouched and renders immediately. Tests directly prove the one thing that must never regress: the fully-accumulated final content is always what's shown once streaming ends, never a stale intermediate value, even if streaming flips off the instant after a content update.
- # **A cheap, honest "thinking" chip — kills both the dead-gap complaint and the no-thought-process complaint.** `app/agents/tutor.py` gains `PlanChunk` (mirrors `TextChunk`'s shape) and `_plan_narration`: one short, separate, cheap OpenRouter call fired before `run_tutor`'s main tool-calling/answer loop, narrating a 1-2 sentence plan via a terse system prompt ("state your plan... under 15 words... do not answer it"). Dormant until `settings.openrouter_api_key` is configured (same pattern as every other optional integration in this codebase); bounded by a strict `asyncio.wait_for` timeout and a blanket `except Exception` — any failure or slowness is fully invisible, the tutor proceeds straight to its normal flow. **Never billed**: constructs its own `OpenAICompatibleProvider` directly against OpenRouter, completely separate from `_select_provider`'s Pro-routing decision, and never touches `billing_service.record_frontier_usage` — a live test with real Pro-frontier routing active on the same turn confirmed exactly one billed call was ever recorded, never two. `chat.py` forwards a successful `PlanChunk` as a `plan_chunk` WS frame ahead of the real answer. Frontend: `App.tsx`'s WS handler sets `ChatMessage.planNarration` (creating the assistant message if `plan_chunk` is the very first frame of the reply, mirroring `tool_start`'s existing first-frame handling exactly); `MessageBubble.tsx` renders it as a new `.plan-chip` (reusing `.tool-activity-chip`'s exact chrome, distinguished by a `--color-info` accent — the same color Learn Mode's `Checkpoint.tsx` already uses for "not a tool call") before any tool-activity chips, gaining the same `--done` treatment once real text or activity lands instead of vanishing abruptly.
  - **Timeout tuned from real live data, not a guess**: the original 3.5s bound (a reasonable-sounding starting point) was actually timing out real, otherwise-successful OpenRouter calls more often than not once tested live — response headers alone routinely took 1-2s, with the first actual content chunk sometimes another couple of seconds past that. Bumped to 8s after confirming (via a raw timed request from inside the deployed container) the model itself isn't slow in general; OpenRouter's real time-to-first-token for this specific tiny system-only completion is just genuinely variable. **Honest residual finding, not swept under the rug**: even at 8s, live testing still saw the plan-narration call miss its window on a real, non-trivial fraction of turns (both a session's first turn and later turns, inconsistently) — this is inherent real-world latency variance on the currently-configured budget model route, not a bug in the feature's logic, and the graceful-silent-skip design is exactly what makes that acceptable: a missed plan chip is invisible, never a delayed or broken reply. Not chasing the timeout higher for now; revisit if a faster route becomes the default.
- # **Auto-generated conversation titles.** `ChatSession.title` was a real DB column nothing ever wrote to; `sessionDisplayTitle` already preferred it when present, so this needed zero frontend read-path changes. New `app/jobs/titling.py`'s `generate_session_title` (modeled directly on `consolidate.py`'s shape: `SessionLocal`, a small transcript prefix, one `get_provider()` call, clean/truncate, write back) is registered in `worker.py` and enqueued exactly once by `chat.py`'s new `_maybe_enqueue_title_job`, right after a session's SECOND assistant reply, gated on `session.title is None` (the job itself also no-ops if a title already exists — belt-and-suspenders, not load-bearing alone). Frontend: after a `done`/`stopped` frame, if the session just got its 2nd assistant reply and its title still looks unset, `App.tsx` schedules exactly ONE bounded `listSessions()` refetch later (not a repeating poll) to pick up the title in the sidebar.
  - **Refetch delay tuned from real live data**: the job's own real model call took ~13.5s wall-clock in live testing — the original 3.5s guess would have refetched long before the job could plausibly have finished. Bumped to 15s; a late (but eventually correct) refetch is harmless, a too-early one wastes the single shot this feature gets.
